[슬라이드 1] 표지   (0:00 부터, 약 53초)

안녕하세요. 스마트보안학과 백종우입니다.

TrustTab 은 결제 증명 기반 리뷰 접근 제어와, 오프체인 AI 판정의 온체인 검증을 결합한 리뷰 DApp 입니다.

프로젝트명은 FairReview 에서 TrustTab 으로 바꿨지만, 이미 배포된 컨트랙트 이름과 서명 도메인 태그 FairReview.AIVerdict.v1 은 서명 호환성을 위해 그대로 유지했습니다.

배포 환경은 Sepolia 테스트넷과 로컬 Hardhat 으로 한정했습니다.

[슬라이드 2] 문제   (0:53 부터, 약 54초)

위협 모델부터 정의하겠습니다.

첫째는 자격 위조입니다. 비구매자가 리뷰를 작성해 평점을 조작하는 시빌형 공격입니다.

둘째는 내용 오염입니다. 대가성 리뷰가 일반 후기와 구분 없이 노출되는 문제입니다.

셋째는 기록 무결성입니다. 중앙 플랫폼에서는 리뷰의 사후 수정과 삭제를 외부에서 검증할 수 없습니다.

따라서 통제 대상은 두 축입니다. 작성 주체에 대한 인가, 그리고 작성 내용에 대한 정책 집행입니다. 기존 서비스는 대개 둘 중 하나만 다룹니다.

[슬라이드 3] 세 가지 해결책   (1:46 부터, 약 81초)

설계는 세 가지 메커니즘으로 구성됩니다.

첫째, 결제 증명입니다. 가게 소유자 권한을 가진 주소만 recordPayment 로 결제를 기록할 수 있고, 리뷰 작성 권한은 해당 결제의 customer 주소에 묶입니다. 결제당 1회, 결제 시각 기준 30일 이내라는 제약을 컨트랙트 상태로 강제합니다.

둘째, 오라클 서명 기반 판정입니다. AI 엔진은 체인 밖에서 점수를 산출하고, 오라클 키가 그 결과에 서명합니다. 컨트랙트는 연산 대신 서명 검증만 수행합니다.

셋째, 인센티브 설계입니다. 결제액의 1퍼센트와 리뷰당 10포인트를 적립하는데, 전송 함수가 없는 양도 불가 포인트로 만들어 2차 시장을 차단했고, 별점과 보상을 분리해 보상이 평점 편향을 만들지 않게 했습니다.

[슬라이드 4] 구조   (3:07 부터, 약 91초)

아키텍처는 세 계층입니다.

클라이언트는 React 기반 웹 앱이고, EIP-6963 으로 MetaMask 공급자를 찾아 연결합니다.

오라클은 Node 서버로, 127.0.0.1 에만 바인딩하고 허용된 출처만 CORS 로 받으며, 요청 크기를 4KB 로 제한합니다.

흐름은 다음과 같습니다. 클라이언트가 결제 번호, 작성자 주소, 별점, 본문을 오라클에 보내면, 오라클은 화면과 동일한 엔진으로 점수를 계산하고 서명을 반환합니다. 클라이언트는 submitReview 에 점수와 서명을 함께 넣어 사용자 지갑으로 트랜잭션을 보냅니다.

설계상 핵심은 오라클이 트랜잭션 발신자가 아니라는 점입니다. 오라클은 가스를 쓰지 않고, 기록 행위의 주체는 항상 리뷰 작성자입니다.

권한은 관리자, 가게 소유자, 고객 세 역할로 나뉘고, 조회는 공개 RPC 만으로 가능합니다.

[슬라이드 5] 관문 7개   (4:38 부터, 약 134초)

submitReview 는 일곱 단계의 검사를 순서대로 수행합니다. 결제 존재, msg.sender 와 결제 고객 일치, 중복 작성 여부, 30일 기한, 별점과 본문 길이 범위, 오라클 서명, 그리고 점수 임계값입니다.

서명 대상 다이제스트는 도메인 태그, chainId, 컨트랙트 주소, 결제 번호, 작성자, 별점, 본문의 keccak256 해시, 점수를 abi.encode 한 뒤 keccak256 으로 묶은 값입니다.

chainId 와 컨트랙트 주소가 포함되어 있어 다른 체인이나 다른 배포본으로의 재사용이 막히고, 작성자와 결제 번호가 포함되어 있어 다른 사람의 서명을 가져다 쓸 수 없습니다. 본문 해시와 점수가 포함되어 있으니, 좋은 점수를 받은 뒤 내용을 바꾸는 바꿔치기도 불가능합니다.

서명은 EIP-191 personal_sign 방식이고, 컨트랙트는 toEthSignedMessageHash 후 tryRecover 로 복구한 주소가 immutable oracle 과 같은지 비교합니다.

점수는 0에서 1000 범위이며, 400 미만은 즉시 게시, 400에서 699는 보류 상태로 저장되어 관리자 판단을 기다리고, 700 이상은 revert 됩니다. 예시 입력의 점수는 각각 0, 550, 990입니다.

[슬라이드 6] 화면   (6:52 부터, 약 46초)

클라이언트 화면입니다.

리뷰 작성 화면은 먼저 오라클 판정을 미리 보여 주고, 거부 판정이면 제출 경로 자체를 렌더링하지 않습니다. 물론 이것은 사용성 장치일 뿐이고, 실제 집행은 컨트랙트가 합니다.

사장님 화면은 recordPayment 트랜잭션의 이벤트 로그에서 결제 번호를 읽어, payment 쿼리 파라미터가 붙은 리뷰 링크를 생성합니다.

빌드 결과물에는 CSP 를 넣었습니다.

[슬라이드 7] 일반 사이트처럼   (7:38 부터, 약 88초)

운영 측면의 개선입니다.

start.mjs 실행기는 오라클 프로세스를 띄우고 health 엔드포인트를 확인한 뒤, 컨트랙트의 oracle 함수를 eth_call 로 조회해 로컬 키의 주소와 일치하는지 검증합니다. paused 상태라면 경고를 출력합니다. 키 불일치는 모든 서명 검증 실패로 이어지기 때문에, 이를 실행 단계에서 미리 차단한 것입니다.

지갑은 eth_accounts 로 기존 권한을 확인해 자동 재연결하고, 체인이 다르면 wallet_switchEthereumChain, 미등록 체인이면 4902 오류를 받아 wallet_addEthereumChain 으로 처리합니다.

결제 기록, 보류 승인, 가게 등록, 두 단계 확인을 거치는 긴급 정지까지 모두 웹 화면에서 처리하도록 바꿔, Remix 의존을 최초 배포로 줄였습니다.

[슬라이드 8] 검증   (9:06 부터, 약 97초)

검증은 세 겹으로 했습니다.

첫째, 테스트입니다. 화면 71개, 컨트랙트 39개, 그리고 오라클과 실행기 단위 테스트가 있습니다.

둘째, 뮤테이션 테스트입니다. 테스트 통과만으로는 테스트의 검출력을 알 수 없기 때문에, 안전 검사 문장을 하나씩 제거한 변이 컨트랙트를 만들어 테스트를 돌렸습니다. 서명 검증, 거부 임계값, 점수 범위, 보류 상태, 오라클 영주소 검사를 포함한 16개 변이를 모두 검출했고, 후반에 추가한 기능 14개도 같은 방식으로 확인했습니다.

셋째, Slither 정적 분석입니다. tryRecover 의 세 번째 반환값 무시, block.timestamp 사용, submitReview 의 분기 수, 이렇게 3건이 나왔고, 각각 의도된 설계임을 문서화했습니다.

CI 는 테스트 실패 시 배포를 차단하고, Sepolia 실환경에서도 게시, 보류 후 승인, 포인트 200 누적을 확인했습니다.

[슬라이드 9] 한계   (10:44 부터, 약 76초)

신뢰 가정과 잔여 위험을 정리하겠습니다.

막은 것은 판정 우회, 결제당 중복 작성과 서명 재사용, 그리고 소유자의 셀프 리뷰입니다.

잔여 위험의 첫째는 가짜 결제입니다. 결제 기록은 소유자의 진술이므로, 오라클이나 PG 사의 결제 증명 없이는 소유자 담합을 막을 수 없습니다.

둘째는 오라클 신뢰입니다. 단일 키이고 교체 함수가 없어서, 키가 유출되면 재배포가 필요합니다. 실서비스라면 키 교체와 다중 서명 오라클이 필요합니다.

셋째, 온체인 데이터는 삭제할 수 없어 개인정보와 충돌할 수 있고, 넷째, AI 엔진의 오탐은 그대로 남습니다.

요약하면, 오라클 서명은 판정의 무결성을 보장할 뿐, 판정의 정확성을 보장하지는 않습니다.
